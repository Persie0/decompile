## Original seam RLE mask is actually materialized with unit fill

- [Pinned full Ghidra 141 #37865506963](https://github.com/Persie0/Playground/actions/runs/37865506963), **2/2 succeeded**. Its `seam-final-mask-138` track decompiled **real function entry `FUN_0043605c`**, rather than inspecting a mistaken address inside the same function. A second original-independent direct ARM64 investigation [checkpoint 142 #38927992170](https://github.com/Persie0/Playground/actions/runs/38927992170) **2/2 succeeded**.
- Original source assembly/decompilation `FUN_0043605c` has a direct virtual call **`(**(code **)(*rle+0x58))(rle,&dense_image,1)`**. The third argument is **literal 1**. The preceding `FUN_004080c4` allocates a crop for the destination region; the routine remaps nonzero binary mask bytes into local cropped destination geometry, using a source/destination height float ratio and **horizontal modulo** to wrap equirectangular x-coordinates.
- `FUN_0043605c` subsequently forwards the remapped mask via destination object virtual `+0x50` and also passes related state via virtual `+0x88`. Checkpoint 142 found this exact helper receives one direct BL from original seam code at raw `0x3344d0`; the parent `FUN_00433478` `seam_mask_generator` function had a lengthy partially damaged Ghidra control-flow decomposition. Therefore the exact *every-mode* last-hop output mask-to-Laplacian blender object identity still needs proof; avoid claiming bit-identical mask image values for every render mode from a single helper.
- As independently recovered earlier, graph-cut temporary RLE expansions and render crop analysis **use fill byte 100** at different callsites. Those temporary values must **not** be propagated into the final 3×3 occupancy blender as 100/9. `PhotosphereRust/src/seam.rs` already implements **0/1 unit masks**, modulo horizontal wrapping, zero-outside vertical bounds and native-inspired `sum / 9` feather on coarser pyramid levels, with `native_unit_rle_mask_expansion_preserves_3x3_wrap_feather` fixture. This new native evidence **supports** the existing choice; no new source change warranted until actual mask-producer-to-blender fixture or a proven mismatch exists.
- `FUN_004371a8` is a different **mask_generator_utils.cc** path and explicitly writes `100` to some mask pixels with `FUN_004a71d4(...,100,...)`. It is therefore incorrect to globally apply `1` or `100` to every native C++ mask: identify the stage and concrete receiver before making changes.

## Source camera correction component still not established in a real capture

- [Ghidra 141 camera track #37865506963](https://github.com/Persie0/Playground/actions/runs/37865506963) independently verifies native `FUN_00431344` initializes a **LinearCamera** with vtable `0x40d540` and sets the optional correction component at struct `+0x30` to **null**. The session-storage path `FUN_0041a6bc` constructs that linear camera from the last image's dimensions then calls `FUN_004440ec` to form a rosette and applies a configured image width through rosette `+0x40`. This is real session-storage behavior, not a universal runtime assertion that *all captured* images use null correction.
- [ARM64 142 #38927992170](https://github.com/Persie0/Playground/actions/runs/38927992170) scans real 64-bit stores to object offset `0x30`: it finds **107** such instructions over a broad geometry code address range. These writes belong to many **unrelated C++ structs** and do *not* constitute 107 camera-lens correction assignments. The original known constructor `0x33134c` explicitly zeroes the correction pointer. Additional same-offset writes require object-identity and callers before assuming distorted capture geometry.
- [Native targeted 143 #38928191254](https://github.com/Persie0/Playground/actions/runs/38928191254) inspects the real camera-model neighborhood and seam generator caller registers to further separate known null initialization from actual runtime pointer installation. Its final result should be inspected before assigning a non-null lens correction or coefficients to the captured phone camera.

**Remaining highest-value gap:** obtain a real original device session with captured source JPEGs, original thumbnail/sample intrinsics, calibration FOV, `orientations.txt`, `session.meta`, and stitched panorama, then compare original projected source pixels / seam masks against the clean-room Rust implementation. Until then, native Ghidra and self-consistency regression tests establish an increasingly faithful approximation, not bit-for-bit Google Camera Photo Sphere parity.

## Checkpoint 143 result: exact native registers and correction-model clone

[SHA-pinned checkpoint 143 #38928191254](https://github.com/Persie0/Playground/actions/runs/38928191254) **passed**. New ARM64 confirms:

1. The seam generator `FUN_00433478` calls `FUN_0043605c` directly from raw **`0x3344d0`**. The helper allocates an area-sized destination mask via `FUN_003080c4` at `0x3360b4`, loads RLE object virtual `+0x58` at `0x3360d8` and invokes it with **`mov w2,#1`** at `0x3360c4`; this is genuine **binary occupancy decode** rather than merely a graph-cut temporary mask.
2. Source-camera **`FUN_003315f8`** allocates a new concrete LinearCamera (`0x38` bytes), initializes **`[new_camera+0x30]=0`** at `0x331630`, then loads **`old_camera+0x30`** at `0x331650`. When old correction is non-null, invokes its **virtual `+0x10` clone** at `0x33165c..0x331660` and assigns that pointer to new `camera+0x30` at **`0x33166c`**, releasing any previous pointer if present. The matching linear destructor functions at `0x331ae8/0x331b18` reset correction to null and release it through its own virtual `+0x08`. This is evidence that the native engine **can propagate a non-null optional correction object** from one calibrated camera to a copy. It is **not** proof that the stock capture FOV pipeline actually created one.
3. Nearby raw `0x331d80` also stores a null pointer at object `+0x30`, but belongs to a **different allocated C++ class** (different vtable `0x40d6f0`), so broad matches of address+offset alone are not camera calibration evidence.

**Next factual target:** find concrete construction / setter of the optional 2D correction object and a capture-session callsite that installs it into `LinearCamera+0x30`, or use a real original session to inspect the live pointer. Until then the no-correction native-linear model remains a valid baseline and the current Rust source lens projection should not incorporate speculative radial/tangential coefficients. No `PhotosphereRust` core change was necessary in this checkpoint.
